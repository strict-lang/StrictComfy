# Ideas
Large or far fetched work for the Moss and H3 programs, moved here from Strict/ideas.md on 2026-11-11. The kernels and the web runtime they name are in ../Strict/Compiler.

- MossImage in the browser (prompt in, encoder, Moss and VAE cached in OPFS, WebGPU like FractalZoomer): the VAE decode runs as WGSL kernels (Compiler/NativeRuntimeWgsl.js) with kept 16 bit maps; next Moss (an int8 GEMM with dot4I8Packed), the encoder, OPFS for the big models.
- WebGPU submits every dispatch in its own command buffer (2300-2700 submits, ~9000 writeBuffer, a new bind group and result buffers per kernel): MossWeb at 480p takes 3.5-4.1 s a step in Chrome on an RTX 4090 against 0.23-0.28 s natively, Chrome's GPU process spends its time in single-threaded Dawn command handling (0.37 ms per batch, a dispatch inside one submit costs 0.01 ms). Batch whole runs of kernels into one command buffer and submit only before a read; the per-dispatch `work` values, pooled inputs and places must stop relying on writeBuffer landing before the next submit (one parameter buffer with offsets), cache bind groups and pool result buffers. The 1 GB queue throttle counts every byte a kernel reads (weights too) and waits ~750 times a step, count only new allocations.
- MossWeb at 1088x1920 takes 43 s per evaluated step on a 3080 (WebGPU): attention stores all scores of a head (8400² is 283 MB), a tiled online softmax would need far less memory and traffic at every size.
- H3 VAE decode on the 4090 (12 s clip, 9.2 s of kernels): strict_device_wholes_fast 41 %, dense attention 16 %, Rope.Rotated 10 % (14650 calls of 61 us), strict_device_blockss 5 % (611 calls of 0.75 ms); H3 sampling steps (5.7 s): routed attention 40 %, int8 GEMMs 41 %. Tried and rejected: tiles of a window as one pass (pixel identical, 2-12 tiles 5-20 % slower, kernels outgrow the L2) and kernels that skip the zero half of the padded 64 wide heads (pixel identical, about 1.5 % of the decode; a loop bound read at run time made it 4 times slower, it must fold at compile time).
- A resident H3Video that encodes with H3 loaded and then drops the text encoder keeps about 15 GB until a later big allocation reuses it (working set 41.7 GB as with the encoder kept, after a full collection and GpuMemory.Released; the same drop before loading H3 ends at 26.8 GB): find what holds it, then a 64 GB machine could keep H3 for new prompts and only load the encoder.

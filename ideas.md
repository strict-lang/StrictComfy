# Ideas
Large or far fetched work for the Moss and H3 programs, moved here from Strict/ideas.md on 2026-11-11. The kernels and the web runtime they name are in ../Strict/Compiler.

- MossWeb still unwinds through Asyncify for every kernel whose pipelines are already compiled (about 1.4 s of a 480p step on a 4090). A separate synchronous record (`strict_webgpu_kernel_fast`) was tried and reverted (Strict 946b17c9, 2026-11-16). Bind groups are still created per kernel. The queue limit has to keep counting uploads: a Galaxy S25 was killed when it did not. Already in: the VAE as WGSL with kept 16 bit maps, the int8 GEMM (`dot4I8Packed`), the encoder and Moss from OPFS, one command buffer until a read or 64 dispatches, staging offsets, a result-buffer pool, and tiled online softmax (the 1088x1920 step stored every score of a head, 8400²).
- H3 VAE decode on the 4090 (12 s clip, 9.2 s of kernels): strict_device_wholes_fast 41 %, dense attention 16 %, Rope.Rotated 10 % (14650 calls of 61 us), strict_device_blockss 5 % (611 calls of 0.75 ms); H3 sampling steps (5.7 s): routed attention 40 %, int8 GEMMs 41 %. Tried and rejected: tiles of a window as one pass (pixel identical, 2-12 tiles 5-20 % slower, kernels outgrow the L2) and kernels that skip the zero half of the padded 64 wide heads (pixel identical, about 1.5 % of the decode; a loop bound read at run time made it 4 times slower, it must fold at compile time). The video VAE file is already int8 with one scale per row (`weight_scale` of shape [rows, 1] plus `comfy_quant`), which is why those GEMMs are wholes_fast; the image VAE's 8 bit load does not apply to it (that file is fp16). Quantizing the tiny float VAE the same way is 0.0044 relative error on one window and is not the path the real file takes.

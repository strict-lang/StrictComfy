# Diffusion inference in Strict: pending work
This file lists only what is still to be implemented: remove an item once it is done (results and numbers go into commit messages or a README), add what is found. Goal: run ComfyUI's Moss (image DiT, RTX 3080) and MiniMax H3 (video+audio DiT, RTX 4090) in Strict, faster than ComfyUI, then plug Strict into ComfyUI through a node.

## Conventions
- Model specific Strict code and fixtures (`Moss*`, `H3*`, `Euler`, VAEs, `tinymoss.safetensors`) live here in StrictComfy, run with `../Strict/strict.exe test|build X.strict`; only generic pieces go into `../Strict` (other sessions work there too).
- `dump.py` (ComfyUI's `python_embeded`) writes reference dumps to `D:\StrictDumps\<name>` (`moss` with the DMD LoRA, `moss-base` without), prompt from `prompt.txt` (not checked in), 720 wide × 1280 high by default. `layer.py` recomputes layer 0 step by step in float32 torch from a dump (`layer0.safetensors`) to find where a port differs.
- Convrot int8 weights load as 8 bit packed rows whose per-32 scales all are the row scale (`Safetensors.Quantized`, exact) and run on the existing int8 tensor core path; activations are quantized per 32 numbers (ComfyUI: per token).

## Moss (RTX 3080)
- Resident backend on 10 GB cards: measured (Performance.md) that keeping the Moss weights on the GPU beats freeing them, ComfyUI streams its text encoder (dynamic VRAM loading). Revisit only if a card can not fit the weights next to ComfyUI's working set: the runtime can already evict device copies of host lists to pinned memory (strict_gpu_evicted), it would need a GpuMemory method to do that for all of them at a job boundary.
- Node: negative conditioning for cfg above 1 (Strict guides against a zero prompt of the positive's length; another length needs its own rotation table).
- Runtime LoRA speed (5.3 s per image against 3.25 s merged): the LoRA epilogue (base + delta / Gain) fused into the expand `Products` (about 0.38 s per image of memory traffic), occupancy of the rank-128 down projection (split-K or a 64x128 tile), the per-image re-uploads (56/31/28 MB x 42).
- Strict's Flux 2 VAE decode 430-450 ms against ComfyUI's 270 ms (the node decodes in ComfyUI), the cold model load (about 3 s against ComfyUI's lazy 0.11 s).
- Grouped Modulated/Rotated vectorization, the full-size Rotated index miscompile, gate/modulation precision alignment.
- Merged LoRAs: per-32 scales for less rounding (stochastic rounding is approximate, 21-25 dB against runtime adapters). Spectrum: adaptive scheduling and ER-SDE are not covered (Spectrum.md).
- GEMM: no emitter change accepted yet, the analysis is in [GemmStalls3080.md](GemmStalls3080.md).

## Phase 2: H3 on the RTX 4090 (blocks developed on the 3080)
Facts: `comfy/ldm/minimax/model.py`, 50 blocks, 5376 wide, 56×128 heads, bidirectional attention over `[text | cond | audio | video]`, modality-tagged adaLN from `adaln_t_table` (curve form), 3D RoPE on the first 96 dims, audio on its own shift-3 clock, 12 s at 480×832 ≈ 36k tokens per step (attention ≈ 60 % of the FLOPs). HyperFlow = rank-256 LoRA merged + 9 fixed sigmas, Euler, no CFG. Video VAE decoder is a 36-block int8 ViT, encoder causal conv3d; audio VAE is BigVGAN.

Kernels per step 3.50 -> 3.27 s (norm weights at 32 bits so Rotated and Modulated run their format copies, fc2's quantize fused, H3Final's loops on the GPU; Performance.md "H3 on RTX 4090"), plain runs 3.6-3.9 s per step since the runtime counts its GPU memory against a fixed budget (30.5 s for the 8 steps, 36.6-39.1 s before). ## Phase 3: Optimization (measured before/after)
- Elementwise work is the whole remaining Moss gap on the 4090 (`Performance.md`: 44.9 against ComfyUI's ~11 ms per step; GEMM, attention and Hadamard are level or faster, steps 187–194 against 223–261 ms). The loops already run at memory bandwidth, so fewer bytes: 16 bit intermediates (../Strict/improvements.md, 16 bit lists on the GPU) and fused passes (norm + modulation, q/k norm + RoPE, situ into the ffn_down quantization, gated residual into the GEMM epilogue); generated by the compiler or as calls into existing kernels is the user's decision. Range analysis for the divisions of generated loops (../Strict/improvements.md) before specialization machinery.
- SageAttention-style attention for sm_89: int8 Q·K with per-block scales, fp8 P·V (biggest H3 lever at 36k tokens).
- Fusions: RMSNorm + modulation + Hadamard + int8 quantization in one kernel, gated residual in the GEMM epilogue, CUDA graphs per block.
- Later: block-sparse attention (FastH3 gate), 0.2–0.3 MP preview paths, F8_E4M3 safetensors if a model needs it.

## Standalone H3Video (idea, 2026-10-28)
ComfyUI's own work dominates short runs: the user's i2v workflow at 0.2 MP with `fastest2steps` takes 23 s, 3.7 s of it sampling. ComfyUI's parts: the 15 GB text encoder moved to the GPU and the prompt encoded (5.3 s, every run with a random prompt), `unload_all_models` moving the text encoder back (8 s inside the Strict node), the video VAE decode 3.6 s, audio 0.5 s, the mp4 1.5 s. Keeping the text encoder in VRAM keeps H3's steps as fast, but the first step after a weight upload took 22 instead of 4 s.
- Goal: `H3Video.exe` runs a ComfyUI workflow on its own (UI or API json: UNETLoader, LoRA loaders, CLIPLoader, MiniMax H3 Image to Video, Strict H3 Sampler or KSampler / SamplerCustomAdvanced, VAE Decode, VAE Decode Audio, Video Combine with NVENC) and replaces the slow parts with Strict code, the ComfyUI node stays. The command line needs no Python since 2026-10-28, the Python command line (`generate.py moss` and `h3`) is gone since 2026-10-29: `generate.py` serves only the nodes.
- Done (2026-10-28): `H3Video.exe [options]` is the command line (`H3Options` with the nested `H3Files`, `H3Batch`): prompt choices, seeds, noise and sampling in Strict; without Python since 18:00: `H3Encoder` (Qwen3-VL 32B NVFP4) encodes uncached prompts (cached in `artifacts/h3`), `H3Vae` and `H3Audio` decode all videos after the last one, ffmpeg writes the mp4s; 27.4-28.9 s warm for the 5 s clip (`--quality fast`) instead of 57.5 s with the ComfyUI workers.
- Order by overhead (2026-10-29, 480x832): the text encoder load for every run with a new prompt (28.9 s, ComfyUI keeps it in RAM; NVFP4 as 4 bit rows would read 15.7 instead of 27 GB; the strict-cd session), the video VAE decode and mp4 (5.3-5.9 s per 5 s video, 10-11 s per 10 s video, half of a `faster` video; video and audio decode 4.2-4.9 s, ComfyUI's first decode of a process 10.9 s and 0.8 s, warm 4.15 s and 0.4 s; the Strict H3 Sampler node decodes in Strict since 2026-10-29, 24.3 s warm for a 5 s `best` video; per tile 17.4 ms int8 GEMMs at 75 % of the int8 peak, 15.0 ms attention in the generic kernel because the tensor core ones take only heads of 128 and the decoder's are 64 wide, about 0.7 s per 5 s video, 7.2 ms idle, 6.3 ms norms and scales, 4.2 ms RoPE; then the 1.3 s of bytes, wav and ffmpeg), the model load (6.4-11 s, TaoMate's merge 14-22 s) and VAE load (2.2-3.0 s), the image to video keyframe encode in the default GPU mode (12.5 s, 0.7 s with `STRICT_GPU=all`, the strict-cd session), the mp4 through NVENC h265 like the user's Video Combine.
